# 昵称、多角色与角色菜单管理

2026-11-05用户新决定优先于旧规格的强制MFA、单角色规则。此文只描述本次身份权限变更，不代表完整V1已完成。

## 用户操作

- 邮箱注册后自动生成含英文字母和数字的随机昵称，已有账号升级时补齐。昵称可在“我的账户”修改，长度1—40字；不作为登录或订单归属依据。邮箱仍用于登录、验证和财务查询，界面身份展示改用昵称。
- 用户管理可一次授予多个角色。角色管理可新增角色、修改名称和勾选菜单；可删除未被账户引用的自定义角色。内置角色不能删除，管理员保留配置、用户、角色、安全及审计入口，避免失去维护通道。
- 同一账户的菜单权限取所有角色并集，服务端每次请求重新查询权限；并非只隐藏左侧菜单。没有按钮权限配置。既有交易的本人不可审核、大额须管理员和财务不能直接核销或审核退款等审批规则继续执行；需要核销或退款审核时可同时授予客服或管理员角色。
- 配置管理 → 账号与安全 → “启用双因素认证策略”，默认开启。开启时只要角色集合含管理员或财务，就必须完成双因素验证，不能通过主角色排序绕过。关闭后使用密码登录且免除该要求；已绑定密钥保留，恢复开启后重新验证。
- 关闭双因素策略须使用有配置管理权限的既有后台会话操作，变更写入配置审计。此开关不等于在已失去全部有效会话和验证器后提供匿名重置入口。密码找回仍不删除已绑定密钥。

## 数据模型与恢复

新增`app_user.nickname`、`access_role`、`access_role_menu`、`access_user_role`。旧`role_name`保留作历史兼容；正式多角色授权以关联表为准，不能只改该旧字段。自定义角色用UUID，旧列只保存兼容内置主角色，避免36字UUID写入旧30字字段。

迁移使用V006_IDENTITY标记，只在首次迁移导入旧角色，不在每次重启时重新授予已撤销的角色。昵称为空时补齐，不覆盖用户修改过的昵称。角色编辑有版本冲突保护；用户角色修改、角色删除使用目录锁防止引用检查与授予并发冲突。用户角色或停用变更会撤销该用户会话。

变更前本地发布工具成套备份数据库及master.key。不要通过删除迁移标记、清空关联表或编辑旧role_name来修复权限；先核对角色目录→角色菜单→用户角色→会话→审计。安全策略值保存在配置数据库中，不要求修改部署配置文件。
